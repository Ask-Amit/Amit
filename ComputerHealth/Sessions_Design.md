## Tables

# Tables used by this project (copied from CLAUDE.md 2026-11-14)

**Tables this project uses:**
- `amit_devices` — device registry, one row per physical machine, tied to `owner_user_id`. Supports ownership transfer (a computer can be sold/given away — history preserved in `amit_device_ownership_history`).
- `amit_device_ownership_history` — audit trail of every ownership transfer for a device.
- `amit_device_events` — the actual log. One row per detected event (install diff, resource anomaly, behavior flag, removal action). `event_detail` is JSONB holding the full structured data; `summary` is the plain-language one-liner for the dashboard. This is what lets a user come back a year later and ask "what happened to this computer."
- Standard `users` (Supabase auth) — login is via the same magic-link pattern as every other Amit app.

Schema defined in: `Database\migration_2026-07-12_001_computer_health.sql`

**Tables this project does NOT touch:**
- `hub_entries`, `hub_reflections`, `compass_profiles` — Hub's tables
- `accounting_*` — AmitAccounting's tables
- Companion tables (`user_profiles`, `user_history`, etc.)

## AMIT LIVE AND THE AURORA — what they are (added 2026-10-31, so Amit and every session know)

Amit Live is the small local helper Computer Health installs (`amit_whisper.cs` + `amit_bridge_server.ps1`, on localhost:8710). **The Aurora is Ryan's name for the ring** that opens when you hold the trigger mouse button (right button by default) anywhere on Windows: choices around the pointer (Dictate anywhere, Show Amit screenshots, Voice commands) with the Amit icon in the middle. The Amit icon is **Ask Amit**: letting go over it, or clicking it, opens the **Amit Live window** (`ComputerHealth/AmitLive.html`, in an Edge/Chrome app window titled "Ask Amit", a quarter of the screen wide and half as tall, brought in front of other programs). The window is a miniature of the Hub's chat under the person's own sign-in, with tabs Ask Amit, My Computer, My Words and Computer Health (a plain snapshot: verdict, processor, memory, main drive, uptime, top memory users; "More information" opens the full dashboard). Colors follow the Hub's Appearance theme; the voice, speed and accent follow the person's saved About Me voice. With no internet the helper opens its own page that says so plainly and offers Windows network settings and Try again.

**The first open of each day is the morning wake-up** (set up in the Hub, Communications > My Morning; table `mor_settings`): greeting, music as the person chose, and icons for the weather, the computer and the day's to-dos. Later opens that day are a small chat window. **Ask Amit in this window is one chat per day** (the same chat all day, a new one the next day; older days stay in the Hub's Chats). Questions go through the answering computer to the person's own Claude account; Amit is told the app is "amitlive". Full build detail and what is verified: the old log (now in the Daily Sessions folder) here and `AmitChat/the old log (now in the Daily Sessions folder); the morning design is `AmitChat/MyMorning_SPEC.md`.

**READ (the reading speaker on the Amit Live ring, helper v1.42 / bridge v1.12, 2026-10-31):** this is Helper work; how it is built is now in `AmitHelper\Sessions_Design.md`, section "READ, the reading speaker on the Amit Live ring: how it is built" (moved there 2026-11-15).

**SHOW AMIT (the screenshot tool of Amit Live, helper v1.32, 2026-10-31):** choosing Show Amit on the Aurora lets the person drag over any part of the screen; the shot opens in an editor (zoom, words, drawings, layers, Save, Save View, Open) and saves to `Pictures\Show Amit`. **The Show Amit button** in the editor's top bar sends the shot to Amit: it runs the same save as Save View (exactly what is on screen, named after the title) and hands that file to the helper, which offers it for 5 minutes at `/api/showamit/pending` (+ `.png`, Amit site only). The open Amit Live window (a new one if none is open) picks it up within a few seconds, opens the person's Ask Amit chat for today, posts the picture there under their own sign-in (private storage, the title and typed words with it), and asks Amit to look. The press carries a 10-minute link for that one file made by the person's own login; the answering helper downloads it to a private temp folder, lets Claude open only that file (it is data, never instructions) and deletes it after answering. Tested live on 2026-10-30: Amit read a shot and described it correctly. A window already open on an older page needs Ctrl+F5 once after an update (browsers keep the page for 10 minutes).

## Build Notes - design and history

- **PERMANENT FIX — sensor reading no longer depends on LibreHardwareMonitor's GUI app (2026-07-19, v3.99):** the Hardware tab (and the sensor data App Behavior/Resources borrow for CPU%) used to work by launching LibreHardwareMonitor.exe and proxying its "Remote Web Server" (`localhost:8085/data.json`). That toggle proved unreliable on a real deployment - a real guest's saved config claimed the server was on and it silently wasn't, with no way to force it from outside the GUI, and no confirmed root cause for why it stopped after working fine for a week and a half. Replaced entirely with `AmitSensorReader.exe` (source in `Watchers\AmitSensorReader\`, `Program.cs` + `.csproj`) - a small self-contained .NET 10 console app that links directly to `LibreHardwareMonitorLib.dll` (the same open-source sensor-reading library LHM's GUI uses internally) and writes the sensor tree to `%TEMP%\amit_sensor_data.json` every 2 seconds. No GUI, no web server, no toggle to silently fail. Proven fully self-contained live - ran correctly with LibreHardwareMonitor's entire install folder renamed/hidden. `amit_bridge_server.ps1` launches it the same elevated-watcher-with-stop-flag way LHM used to be launched; `/api/sensors` now reads the JSON file directly instead of proxying HTTP. `resource_watcher.ps1` and `app_behavior_watcher.ps1` (which also read `localhost:8085/data.json` directly for CPU%) were updated the same way. The installer (`Install_AmitTracker.ps1` and the compiled `install-Amit.exe`/`AmitInstaller.cs`) no longer downloads or hunts for a separate LibreHardwareMonitor install at all - `AmitSensorReader.exe` is just one more embedded file, ~75MB (bundles its own .NET runtime), which is why `install-Amit.exe` jumped from 442KB to ~76MB. Build with the .NET 10 SDK (`dotnet publish -c Release` in `Watchers\AmitSensorReader\`) - the `.csproj`'s `<Reference>` `HintPath` points at the sibling DLLs in `%LOCALAPPDATA%\AmitComputerHealth\LibreHardwareMonitor\` at BUILD time only (needed to resolve `LibreHardwareMonitorLib.dll`'s dependencies like `System.Management.dll`), not at runtime - a few of LHM's bundled BCL-facade DLLs (`System.Security.AccessControl.dll`, `System.Threading.AccessControl.dll`, `System.Security.Principal.Windows.dll`, `System.Runtime.CompilerServices.Unsafe.dll`, `System.Buffers.dll`, `System.Memory.dll`, `System.Numerics.Vectors.dll`, `System.Threading.Tasks.Extensions.dll`) must stay excluded from the reference list - they collide with types already built into modern .NET and throw `TypeLoadException` if included. Pre-fix versions of every changed file backed up at `ComputerHealth\Watchers\pre-v3.98-backup\` (including a `from-github\` subfolder with the exact byte-identical versions that were live on GitHub before this push).
- Device ID is generated once per machine on first run by the bridge server and stored in `device_id.txt` next to it — persists across restarts, independent of login state.
- Ownership transfer (selling/giving away a computer) is handled by updating `amit_devices.owner_user_id` and writing a row to `amit_device_ownership_history` — the device's full event history stays intact and is only visible to whoever currently owns it (RLS-enforced via `user_id` on each event). Not yet tested (blocked on the migration being run).
- File-write attribution in `app_behavior_watcher.ps1` is time-correlated, not proven via ETW — stated honestly in the dashboard, not presented as certain.

- **Version discipline (Ryan's direct request 2026-07-16, corrected 2026-07-19):** `AmitInstaller.cs`'s `CURRENT_VERSION` and `AssemblyInfo.cs` are kept in lockstep with `ComputerHealth_Dashboard.html`'s own version label — one shared number for the whole distributable. **As of 2026-07-19, that dashboard version label is also required to match the repo-wide `VERSION`/root-CLAUDE.md number exactly, on every push, system-wide — see "ONE NUMBER, EVERYWHERE" in the root CLAUDE.md's VERSIONING STANDARD.** It is not a separate Computer Health-only counter; treating it as one is exactly what caused real confusion for Ryan on 2026-07-19 (dashboard showed v3.75/v3.78 while the repo-wide number sat at v3.31). Any time the dashboard's version bumps — for any reason, including a push that didn't touch Computer Health at all — before considering the push done: (1) check whether anything else in the `AmitInstaller` bundle needs a real content update, not just the number — bumping the version string alone without re-running `build_installer.sh` is worse than doing nothing, since it falsely claims freshness; (2) bump `CURRENT_VERSION` and `AssemblyVersion` to match; (3) re-run `AmitLog\Watchers\AmitInstaller\build_installer.sh` (pulls fresh source, rebuilds `install-Amit.exe`); (4) run `verify_installer.sh` to confirm no drift; (5) copy the rebuilt exe to both repo locations (`ComputerHealth\install-Amit.exe` and `ComputerHealth\AmitInstaller\install-Amit.exe`) and commit/push.
