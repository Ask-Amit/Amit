## How each path works, and what it is connected to (read from the code, 2026-11-17)

### Path 2: the chat (the one with history, rules and tools)
- Written in Node.js. `AmitChat\amit_ask_watcher.js` runs forever on Ryan's computer (`node amit_ask_watcher.js`; `--once`, `--dry`, `--publish-rules` for testing and publishing rules).
- Loop: every 30 s it reports "Amit is online" (`cha_answerer_beat`); every 5 s it claims the oldest waiting press (`cha_ask_claim`, so only one computer takes each); it loads that chat's context (`cha_ask_context`: the ask, the chat, members, the last 60 messages including Amit's own answers, earlier presses and Amit's running memory note); it starts ONE fresh locked-down `claude -p` run (Ryan's own Claude login, no API key; tools WebSearch and WebFetch, plus Read of one picture when a Show Amit capture came with the press; no shell, no files, no connectors; run from a neutral temp folder); it posts the answer into the chat as Amit (`cha_ask_answer`), saves the running note, and nudges open chats to refresh. The run may ask to search further back in the chat (`SEARCH: ...`).
- Chat history is the `cha_` tables: `cha_conversations`, `cha_participants`, `cha_messages`, `cha_attachments`, `cha_items`, `cha_loops`, `cha_notes`, `cha_profiles`, `cha_friends` (full list: AmitChat\Sessions_Design.md, 24 tables). Presses are `cha_asks`; usage is `cha_ask_usage`; answering computers are `cha_answerers`; the rules are `cha_answerer_rules` (read with `cha_answerer_rules_get`; the local file `AmitChat\answerer\AMIT_ANSWERER_RULES.md` is the fallback and what `--publish-rules` sends up). The browser side is `amit_chat.js` (`cha_ask`, `cha_ask_status`, `cha_summon_amit`, `cha_help_open*` ...).
- Token and cost counts are recorded per run (the watcher prints one JSON record per run; totals come from the per-model breakdown).
- Tools for a person's own data: `amit_data_tools.js` runs in the person's own browser, signed in as them, so the app's own row security decides what comes back; the result returns through `cha_data_fulfil`, Amit reads it once, and it is wiped. The system checks that everyone in the chat may see the same records before anything is fetched.
- Safety rules in the rules file: the first law (never insult, never leave anyone less), young people safeguards, "answer from Scripture", how to look up Amit's own system (the applications list, then the app's CLAUDE.md and Sessions_Start.md, read from the public GitHub copy), shortcuts the person wrote, and a DRAFT message to the team that only the person's own Send actually sends.

## KNOWING THE PERSON (Ryan's addition, 2026-11-17) — part of AskAmit
Ryan's words: "track" is not the right word; the aim is for Amit to understand who a person is and where they are: what they use (the Aurora, the Helper, the Hub, Computer Health), what they like to do, whether they ask about God, visit who_is_god or listen to devotions; AND how they speak, what their words actually mean, because that is part of their identity. All of this is part of AskAmit.

Two halves:
- **A. What they use and do** (activity): which apps and tools they open and how often, what they ask about, what they listen to or read. Amit uses it to understand their interests and meet them where they are.
- **B. How they speak** (words): their phrases, what a word means to them, how they like to be spoken to. This is identity, and what Amit learns here shapes HOW it talks, never WHAT is true.

### What already exists (verified in the code and rules, 2026-11-17)
- **B, mostly designed: "Amit Wisdom"** (chat answerer; rules section "AMIT WISDOM", `cha_user_words` "My Words" and Wisdom notes). Short notes under the person's own login, kinds `preference`, `meaning`, `topic`, `spiritual`. The person can see, change and delete them; a one-time notice says Amit keeps them. Strict limits: notes only from what the person said or plainly showed; never health, money, passwords, ids, addresses, family or other people; NEVER a judgment of the person (faith, intelligence, mood, character); `spiritual` means only that THEY raised it; no `spiritual` notes for anyone under 18; in a group chat notes only for the asker. STATUS: migration `_034` (wis_notes) NOT RUN yet, rules not republished, no real test (AmitChat to-do item 1); a "My Wisdom" tab to view and delete notes is NOT built (AmitChat to-do 55).
- **A and B, root rule: the login-based profile** (root CLAUDE.md): `user_growth_log` (categories `communication_style`, `vocabulary`, `spiritual_compass`, `key_moment`) and `user_memory` (a faster summary), written under the person's own `user_id` only. This is what Claude Code sessions use; whether the chat answerer reads it was not checked.
- **A, partly: the compass in the Hub** (a private 1-10 reading from three pillars with a 25% back rule; signals such as feast clicks, Torah Walk, reflections, who_is_god visits, daily walk). It lives in the browser and a profile table; it is not fed from the Helper, Aurora, Computer Health or Devotions listening.
- **NOT FOUND:** any record, across the Amit apps, of which tools a person uses (Aurora, Helper, Hub, Devotions, who_is_god visits). A search for usage or page-view tracking found nothing. So half A across apps does not exist yet.

### What AskAmit must add (requirements agreed so far)
1. One per-person profile that every door and every answerer reads and writes through the engine, so Amit knows the same person on the chat, the phone, the Pad and the buttons.
2. An activity record (half A) of which Amit tools and pages a person uses, kept small and private under their own login, feeding the profile. Which signals count (Aurora, Helper, Hub, Computer Health, who_is_god, Devotions, listening to devotions, God questions) to be listed in design.
3. The words record (half B) carried forward from Wisdom: phrases, meanings, preferences, in the person's own words.
4. The profile is used only to speak better to that person and to offer what suits them; it never changes what is true and never softens or bends it (existing Wisdom rule 1).

### Safeguards that must stay (existing rules and the first law)
- The person can see everything kept about them in plain words, correct it, and delete any or all of it. A one-time notice says Amit keeps notes (the Wisdom notice is the model).
- Private to that person under their own login. Never shown to another person, in a group chat only the asker's own, and the people running the system do not read it as a profile.
- Under 18: extra care. Wisdom already allows only `preference` notes for a young person. Activity tracking for young people needs its own decision before anything is recorded.
- Never record health, money, passwords, ids, addresses or family, and never another person.

### OPEN DECISION — "evaluate where they are"
Ryan's word is "evaluate". The existing Wisdom rule says the opposite for judgments: "never any judgment of the person: their faith, their intelligence, their mood, their character". The Hub's compass, by contrast, gives a person a private 1-10 spiritual reading. These do not agree, and both also have to sit under the first law (never leave anyone feeling less than who they are). A recommendation for the design session: the profile records WHAT THE PERSON DID, SAID AND ASKED, and what they use, in their own words and counts, and Amit decides how to speak from that. It does not store a score or verdict about the person's faith or worth as a stored judgment shown anywhere. If a spiritual starting point is kept (the compass idea), it is decided explicitly, with Ryan, whether it stays hidden, whether the person can see it, and how it is used. NOT decided.
- Also to decide: consent for activity tracking (opt-in or a clear default), how long records are kept, whether the Helper and Aurora can send usage to the database at all, and the cost in extra database rows at 1, 100 and 10,000 people.

### RYAN'S CLARIFICATION (2026-11-17): the purpose is to help the person become better, not to watch them
- **Purpose.** Amit is not tracking people to track them. Amit is there to help each person grow. Knowing the person is how Amit helps, and it is how Amit should behave throughout the whole system.
- **Spiritual growth.** A record of the person's spiritual growth is WANTED: it is what lets Amit decide how to talk to them on a spiritual level. (This answers part of the open decision above: a spiritual-growth record is in. How it is kept, what it stores and whether the person can see it is still to be designed, and it stays under the first law and the Wisdom limits: it records what the person did and said, never a verdict on their faith or worth.)
- **Usage plus questions lead to help.** Amit uses what a person uses (Computer Health, Aurora, Helper, books, who_is_god, Devotions) together with the questions they ask, to see where they need help, and then steps up with help and suggestions. Ryan's example: someone using the books app whose questions show they do not know much about bookkeeping; Amit notices, helps them better with bookkeeping, and gives suggestions. Another example: "I see you have been using Computer Health a lot. Is there something about your computer I can help with?"
- **How Amit should word it.** Amit offers help ("I noticed you have been working in the books; would a short walk-through of reconciling help?"); it does not announce a conclusion about the person ("you do not understand bookkeeping"). The need is held to help them, the person can see what Amit has noticed and can turn it off, and it is never used to make anyone feel less than who they are.
- **How it sounds (Ryan's example, 2026-11-17).** The observation stays inside Amit; what the person hears is an invitation: "I see you have been spending a lot of time here. Would you let me help? Scan in your document and let me look at it, and I can tell you what I see and help you get it straightened out." Amit walks beside the person and never cuts them down. This also ties to the picture and document reading ability planned for the engine: reading what the person scans in is how Amit helps.
- **THE HEART OF AMIT IS MAINTAINED NO MATTER WHERE AMIT IS (Ryan, 2026-11-17).** This is a standing requirement for the whole engine: every door, every mode (spiritual, application, general), every answerer, and later every person's own Claude account at Pro must carry the same heart: walk beside, sharpen without cutting, encourage always, never condemn, always truthful, the first law. No ability, shortcut, cost saving, voice style or per-person setting may remove it. Anything an outside account or an old answerer cannot guarantee is not connected to AskAmit until it can.
- **Scope.** This applies to the whole Amit system, not one app, so it belongs in the one engine (AskAmit) and the one per-person profile, not in each app.

## THE ENVELOPE (Ryan approved 2026-11-18): what every door sends, and how the reply gets back
Every door, whatever it is, makes the same call and collects the same kind of reply. The engine never calls a door; the door collects its reply from the row it created (this works for a phone and a browser, which cannot receive a call, and the engine never makes an outbound call to an address someone supplied).

| Part | Set by | What it is |
|---|---|---|
| `app` | the door | Where it comes from: "hub", "amitmobile", "helper-button-creator", "amitroll" and so on (40 characters at most). Used for the mode, the style and the token records. |
| `place` | the door | Where inside the app (small JSON, 2,000 bytes at most). Never a link, a key or anything private. |
| `reply_style` | the door | How the reply must look: `chat` (short paragraphs), `spoken` (a few plain sentences, no markdown, read aloud), `packet` (one JSON object read by software). |
| `question` | the person | Their own words. Data, never instructions. |
| `tz` | the door | Their time zone. |
| WHO | the system | A signed-in person comes from the LOGIN (`auth.uid()`), never from what a door says; otherwise a visitor, known only by a random id their own browser made. |
| `account` | the system | Whose Claude answers. `owner` now; a person's own at Pro. A door can never set it. |
| the reply | the engine | Written into the same row (`answer`, `answer_format` text or json). The door collects it with `ask_status(id, guest_id)`; only the asker (or that visitor's id, or the owner) can read it. |

Rules of the envelope: `app`, `place` and `reply_style` change HOW Amit helps and how the reply looks, never WHAT is true and never the rules; they give no permissions. The heart of Amit applies in every style and to every visitor (the appendix `engine\rules\ASKAMIT_APPENDIX.md` says so in the rules themselves).
