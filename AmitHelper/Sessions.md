### 2026-11-11 - Amit Keyboard: secure messages between people (IDEA / DESIGN NOTES ONLY, nothing built, nothing changed, discussed with Robin)

**THE FULL, STAND-ALONE RECORD OF THIS DESIGN IS `KEYBOARD_SECURE_MESSAGING_DESIGN.md` (this folder), written 2026-11-11 so a later session can resume from it cold. Read it first; the notes below are the working log it was made from. Also decided 2026-11-11: English only for now (no Hebrew, emoji or other characters). A SECOND idea (phones and peripherals, how data gets into a computer) is still being brainstormed by Robin and is not captured: ask where it went when resuming. The phone-data answer given on 2026-11-11 is recorded in section 9 of the design record.**

Technical discussion, no build. What exists today: Amit Keyboard (Helper 1.88, Hub `AmitKeyboard.html`) has the tabs Secret code, Secret modifier and Secret decipher: a keyboard set that swaps the key a person presses for another (for example K types T) so what they type comes out coded on their own computer, and the decipher tab turns it back. It works on one computer at the keyboard level (the Helper's key hook). It is not yet connected to the chat or to another person. To be elaborated later (not now).

**The idea, as said (Robin, by voice):**
- **Two levels, a new kind of keyboard set.** "Security level sets" are a separate kind of set: they do NOT show in the normal, programmable list of keyboard sets (which a person can change freely); they get their own button/tab.
- **SECRET level:** no code word and no modifier. A fixed set of key swaps (K is T, and so on) used both ways. A normal outsider who gets the text cannot read it because they do not have the set and cannot work out the keyboard. Meant for about 90% of use, between systems and people.
- **TOP SECRET level:** the same plus a modifier, so every message is scrambled differently. The scramble depends on the **date and time** of the message. The sender's own computer scrambles it before it is sent, never the plain text over the wire; the receiver already has the date and time (stored with the message), so they can recalculate what the keyboard looked like at that moment and decipher it. A reply has its own time stamp and date stamp and goes the same way back.
- **A digital keyboard display (top secret):** on the sender's computer a drawn keyboard shows what each key will become for that date and time (on this keyboard A is J). The person presses the keys shown, or types and the program does the swap; the chat gets the scrambled text.
- **Delivery:** both people must be signed in to the Hub (the Hub is tied to the database), so messages travel the way the chat already does and land like an inbox: date, time and who sent it are already stored. The chat gets **three toggle buttons at the bottom: Normal (anyone can read), Secret, Top secret.** A person can authorize ("send secret keyboard sets 1 to 5") so the other person receives the sets through the chat and database.

**Amit's assessment (said to Robin in chat; recorded so the next session does not start from zero):**
1. The experience is good and fits the existing pieces (the chat toggles, the keyboard sets, the date and time already stored).
2. A key-swap code is **obfuscation, not encryption**. A fixed swap (the Secret level) is broken by frequency counting in a few messages by anyone who tries; it stops a casual reader, not a determined one. A top-secret swap that depends ONLY on the date and time is only as strong as the secrecy of the way it is worked out, because the date and time are not secret. The strength has to come from a shared secret (the set) mixed with the time.
3. **Sending the sets through the same chat/database defeats them**: whoever can read the chat can read the sets. The sets must reach the other person another way (in person or another channel), or be wrapped with real encryption (the global PIN Encryption, AES-256, `amit_pin_encryption.js`) before they travel.
4. Better design on offer: keep the keyboard feel on screen, but let real encryption (shared secret + time stamp feeding the scramble, or AES underneath) do the work, so what looks like a scrambled keyboard is also genuinely safe. The decipher-from-time idea is sound and stays.
5. The real benefit of "scrambled on the sender's computer first" is that the plain text never reaches the database, the Hub or the team: that is worth keeping whatever method is chosen (it matches the data security model: chats locked to the team, Amit not reading what it should not).

**ADDED same day (Robin): the security-level sets live ONLY on each person's own computer as local configuration files, never in the database**, and are handed to the other person by a different route, so a break-in to the database yields only scrambled text. Amit's notes on it: (1) good, and it matches the existing rule that the Secret modifier's secrets are never saved anywhere; (2) the database would still show WHO wrote to whom and WHEN (metadata), never the content or the key; (3) because the sets are local, the chat page cannot read them itself: it must ask the Helper over the shared bridge (`localhost:8710`, a new route, per the SINGLE LOCAL CONNECTION STANDARD), so the scrambling runs in the Helper, which changes decision (c) below toward the Helper; (4) the local file should itself be kept encrypted under the person's PIN (global PIN Encryption), so a stolen computer does not hand over the sets; (5) a lost or reinstalled computer means lost sets and unreadable old messages, so an optional encrypted export (PIN-protected) is needed; (6) ways to hand sets over: in person, a drawn QR code scanned from the screen, a PIN-protected file, a printed sheet, never the chat or database.

**Open decisions for Robin/Ryan (not yet answered):** (a) is the aim a game-like code, or real secrecy? (b) how the sets are given to the other person; (c) where the scrambling runs: in the chat page (works without the Helper) or in the Helper's key hook (works in any program); (d) what happens to characters not in the set (spaces, numbers, punctuation); (e) whether the online answering Amit may ever read secret messages (recommended: never).
**DECISIONS MADE (Robin, 2026-11-11, answering (a) to (e) above):** (a) REAL secrecy, not a game. Purpose as Robin states it: a way for believers to talk when everything is watched (the persecution Scripture describes at the end of the age), and a free, simple way for a company to message staff worldwide; more people signing up means more use, more revenue to pay for it, more witness. (b) The sets reach the other person by whatever route that person chooses, by hand, by letter ("this is data set 5"), by phone, even as a chat attachment; the level of safety is the person's choice (Amit's note: the screen should say plainly that a set sent through the chat is only as safe as the chat). (c) The scrambling runs in the CHAT PAGE first (secret messages are only ever typed inside Amit, not in Word); the local-file/Helper route stays as noted above for reading the local sets.
