## 1. What this is, in one paragraph

A person who is not technical builds a button by SPEAKING to Amit. Amit asks the few questions it needs, builds the whole button (name, icon, description, the profile it belongs in, the recipe in plain words, and the code or steps that make it work), checks it against the never list, seals it, and posts one sealed packet in the chat. The person presses Insert. The Hub checks the seal belongs to the signed-in person, installs the packet on the button, and the normal bar sync sends it to the helper on the computer. The person can press Test, but never sees or edits the code. To change anything, they go back to Amit. The button works on the computer without Amit being asked again, even if Amit, the Hub or the internet is down (only steps that open a website or an Amit page need the internet).

The simple (manual) way of making buttons with the drop-down menus stays exactly as it is. "Ask Amit to create this button" is a second button next to it, for complex buttons.

## 2. Decisions Ryan made (do not re-discuss)

2. Every person gets the code box, not only Ryan, because Amit makes sure it is safe while creating it. The first version is proved on one button on Ryan's own computer.
3. The packet is copy and paste (or one-click Insert). It carries authentication tied to the login. If it does not match the signed-in person, it does not install ("Amit did not create this code for you, so it will not run here").
4. The person never sees the code and cannot edit it. Only Amit recreates or changes it, starting from the recipe kept in the packet.
5. The never list (confirmed): (a) deleting, formatting or emptying drives or folders; (b) changing system or security settings; (c) downloading something and running it; (d) collecting passwords or personal data; (e) buying, unless the person confirms each purchase [REVISED 2026-11-24, Ryan: "sending messages, posting" were REMOVED from the never list so a button can answer email, check ads, change prices; "buying" kept with per-purchase confirmation as Amit's recommendation, Ryan's answer on buying was cut off, confirm it]; (f) anything that needs administrator rights; (g) hiding what the code does. Anything that writes to the person's files makes a dated backup copy first. SAFEGUARDS THAT REPLACE the old sending rule (2026-11-24): (1) the first-run approval box names plainly what the script sends, posts or changes and where, and asks again whenever the script changes; (2) a practice (dry) run shows what it would send without sending, and the person must confirm the first real run; (3) a log of every send, post or change (what, where, when) the person can read; (4) a limit per press (for example 20 messages), the person can raise it; (5) rule (d) stays: the script never collects passwords, it uses what the person is already signed in to, and any key is entered once in the helper, never seen by the script. 6. Amit refuses a button that breaks the never list and says plainly why, in the chat, while it is being created.
7. The packet also carries the title, the icon, and where the button should live (which profile; Amit is told the existing profiles; it may suggest a new one).
8. Keep it simple: do not rewrite what exists. Build ONE button end to end first, then widen.
9. Free-text is only ever data; the simple drop-down buttons keep using only the fixed safe steps.

## 3. How it is built (the design)

**Seal.** A digital signature (RSA-2048 with SHA-256; works in both Node and the .NET the helper uses). The private key stays on Amit's side only (a local-only file next to the Ask Amit watcher, never in GitHub, never in the Hub page, never in the helper). The public key ships in the helper. The signed text includes the exact code, the recipe, the person's login id and the packet version. Change one letter and it fails. A tag with only the login id would NOT be enough (anyone could type it).

**Who stamps.** Not the chat model. The model writes the packet; ordinary software (the Ask Amit watcher on Ryan's computer for the first version) runs the CHECKER (shape rules, never-list scan, size limits) and only then stamps. A prompt-injected chat must not be able to get something stamped. The stamp proves who made it, not that it is safe; safety is Amit's refusal + the checker + the person's approval on each computer + the backup rule.

**Where the pieces live.**
- Database (`hel_buttons`, migration to write; Ryan runs it by hand): new columns `code` (text, the sealed packet), `recipe` (text), `code_computers` optional. Own rows only (already). Writing `code` is allowed for the signed-in owner; the seal is what makes it trustworthy, checked at the helper.
- Hub (Communications > Amit Helper): the button pop-up gets "Ask Amit to create this button" and an "Insert packet" box. No code is displayed. "Test on this computer" asks the helper to run it.
- Helper (`amit_bridge_server.ps1`): the stamp checker, the login-id match (the Hub sends the signed-in id with the bar), a route to report its computer name and id, a route to run a button for Test, and writing the verified code into that button's entry in `amit_bar.json`. Delivered by the normal update (six lists, see memory `reference_helper_file_lists.md`).
- Bar (`AmitBar.cs`, rebuilt by Update and reload): runs the button's code, only after the person approved THAT code on THIS computer (approval is stored locally, tied to a hash of the code, so any change asks again). Shows a plain-words summary in the approval dialog.
- Ask Amit (the existing chat): a "button creation mode" opened by the Hub with a safe handoff (the Hub's Ask Amit takes nothing in the address by design; use a one-time handoff, draft only). Needs the Button Builder instructions published to the answering Amit (`AmitChat\answerer\AMIT_ANSWERER_RULES.md` family; publishing rules to the live answering Amit waits for Ryan's say, see memory `project_answering_amit_safety_2026-10-26.md`).

**What Amit is told about the computer (with the person's consent, shown what is shared):** the profiles that exist; the installed programs (the helper's `/api/programs`); the list of Amit apps (Living Testimony list); the list of things the helper can do today.

**Computer registration.** The helper knows its own computer name and id. When the person approves a button's code, that computer is recorded for that button. Code is never sent down to a computer the person has not approved it on.

**Returning the packet.** A "Use this packet" button under Amit's message creates/updates the button in the right profile in one click (copy and paste stays as the fallback). Changes: the person says what to change; Amit sends a new packet; Insert replaces the old one; the chat history is kept.

## 4. The packet (before sealing)

```
{
  "v": 1,
  "name": "Daily books",                // up to 24 letters
  "icon": "a character from the icon library",
  "description": "shown on hover, up to 200 letters",
  "profile": "Books",                    // an existing profile, or a new name to create
  "recipe": "the plain-words recipe: what the person asked for and what Amit built",
  "summary": ["what it will do, in short plain lines", "what it touches"],
  "steps": [ { "t": "open_app", "v": "AmitBooks" } ],   // safe steps where they are enough
  "code": "the code the helper runs locally (only when steps are not enough)",
  "touches": ["files it writes to"],     // used for the backup rule and the approval dialog
  "user": "the signed-in login id",
  "seal": "the signature (added by the stamping software, never by the model)"
}
```

## 5. The interview (the Amit question set)

Amit speaks plainly and warmly (the testimony's "How I treat every person"). One question at a time. Ask only what is needed; never lecture. The first message of the mode:

1. "You're creating a button. What would you like to call it, and what do you want it to do?"
2. Then, only as needed: "Where does it need to go first?" (an Amit app, a website, a program, a folder, a file) / "Once you get there, what should happen?" / "Anything extra, like a file opened, a number typed, a sound played?" / "In what order?" / "Should it ever change or save something? Which file?" / "Which group does this belong in?" (offer the person's profiles, or a new one) / "Is this the right icon?" (offer two or three from the library and say why).
3. If the request touches the never list: refuse kindly, say why in one or two sentences, and offer the nearest safe version ("I can open the folder for you, but I can't empty it").
4. If it needs something the helper cannot do yet: say so plainly and record it as a missing ability (becomes a to-do), do not pretend.
5. Before finishing: a short plain summary of what the button will do and what it touches. Ask "Shall I make it?"
6. Post the packet once, then: "Press Insert under this message. Press Test to see it work. If anything is off, tell me and I will change it."
